## Goals / Non-Goals

**Goals:**

- Adopt exact OpenSpec `1.7.0` and preserve Node `>=20.19.0`.
- Preserve the exact six-skill core allowlist and isolated, telemetry-disabled,
  project-local activation model.
- Treat all six regenerated skills as one atomic versioned batch.
- Keep OpenSpec proposal/design/spec/tasks canonical and DevFlow responsible for
  routing, gates, execution evidence, release, and archive authorization.
- Prove source, package, generated runtime, and isolated/local project behavior.

**Non-Goals:**

- Tracking npm `latest` dynamically or consuming upstream `main`.
- Adding the other OpenSpec workflow skills published outside the `core`
  profile.
- Enabling OpenSpec stores, custom schemas, operation guidance, or `skip_specs`
  as new DevFlow defaults.
- Fixing the pre-existing installed-cache versus development-source root
  identity false positive.
- Archiving changes, creating a PR or GitHub Release, upgrading unrelated
  dependencies/plugins, applying unrelated project migrations, or cleaning
  legacy files.

## Decisions

### 1. Pin exact 1.7.0 and retain the existing provenance boundary

The dependency record, installer, updater, smoke test, and generated-skill
verification SHALL use `1.7.0`, not an unbounded dist-tag. Registry `latest`
remains diagnostic evidence only.

Rejected: stay on 1.6 (misses relevant correctness fixes), `@latest` in apply
commands (non-deterministic), and upstream `main` (unreleased).

### 2. Keep isolated core generation unchanged

The existing command and temporary `XDG_CONFIG_HOME`, `CODEX_HOME`, and
`OPENSPEC_TELEMETRY=0` environment are already compatible with 1.7. The source
root remains staged `.codex/skills`; verified copies remain project-local
`.agents/skills`. No global prompt or profile migration is needed.

Rejected: using static upstream skill files directly, running `openspec update`
against the live project, or mutating global OpenSpec profile state. Each would
bypass DevFlow's exact-set/transaction boundary.

### 3. Accept 1.7 guidance as OpenSpec-owned input, not a second workflow owner

The six released skills may read `openspec/config.yaml` context, artifact rules,
and operation guidance. Those inputs remain subordinate to CLI state, explicit
user choices, OpenSpec artifacts, and DevFlow gates. They neither prove task
completion nor authorize sync/archive/release.

### 4. Rename version-specific regression coverage and preserve exact behavior

The 1.6-specific integration test module becomes a 1.7-specific module. Tests
first encode the new expected version and generated bytes, fail against the old
pin, then drive the smallest source updates. Generic isolation, rollback,
custom-target, and exact-set behavior remains unchanged.

### 5. Separate source/release adoption from external rollout boundaries

Source and generated `plugins/dev-flow` release counterpart are part of the
implementation. The explicitly named OpenSpec CLI/project skill update may run
only after source and release verification. Plugin cache refresh is limited to
`dev-flow@cy-codex-skills`. The user's 2026-08-04 follow-through instruction
separately authorizes scoped commits, native Git push directly to the verified
`origin/main`, and post-push refresh/readback of that named cache and this
project's six skills. Archive, PR creation, and GitHub Release publication
remain separate and are not performed.

## Risks / Trade-offs and Rollback

- [All six skill bytes change] → verify the exact set and version as one staged
  transaction; never mix 1.6 and 1.7 copies.
- [New operation guidance appears authoritative] → tests/docs preserve OpenSpec
  artifact and DevFlow gate precedence.
- [Interactive stale-version check introduces network or mutation] → generation
  keeps `OPENSPEC_TELEMETRY=0`; updater uses exact explicit install commands.
- [Global 1.7 install fails] → preserve verified source/release work, keep or
  reinstall exact 1.6.0, and do not refresh project skills/cache.
- [Project refresh encounters custom content] → fail closed and preserve it;
  do not force replacement.
- [Release counterpart fails] → stop before local rollout and leave the current
  installed plugin/CLI untouched.
- [Remote is no longer fast-forward] → preserve the local commits, fetch/read
  back the divergence, and stop rather than force-push or merge implicitly.
- [Post-push targeted refresh fails] → keep the pushed verified release,
  diagnose only the named cache/current project, and stop before unrelated
  updater or migration actions.

Rollback is exact: restore the 1.6.0 provenance/source commit, reinstall
`@fission-ai/openspec@1.6.0` only if an applied 1.7 runtime fails, and restore
the six project skills through transaction evidence. Do not change global
profiles or delete legacy/user-authored files.
